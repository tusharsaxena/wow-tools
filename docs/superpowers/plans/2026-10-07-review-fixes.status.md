## Decisions taken during the build

- T1.1: no `CHANGELOG.md` line. The fix only changes behavior for a hand-edited or corrupted journal, so it is not user-noticeable on any normal run (STD-11.1); the 04 plan's T1.1 file list also leaves it out.
- T1.1: the flavor list also feeds `_prune`, so a crafted flavor no longer reaches pruning either; the review's sketch was followed as written.
- T1.1: the review's UI finding was taken as real: the Undo popups' rows now come from the same `undo_flavors` helper as `undo_run` (re-exported by each tool's `undo.py`, as `destination` is), instead of only rewording the comment.
- T1.2: `wow_root` is a required keyword of `recover` (no fallback to the marker's `flavor_path`), per R3; every existing caller and test passes it.
- T1.2: the `to_stored()` write lives in the shared `core/marker.write_marker`, so the WTF Cleaner's `clean-in-progress.json` is stored in Windows form too; its `read_marker` reads with `to_native()` (a marker only produces a notice there, so no behavior change beyond portability). Older `str()` markers still read.
- T1.2: the flavor check runs first, before the WoW-running check, so a marker for a game version that is not in the configured WoW folder is refused with "<flavor> is not in the WoW folder <path>. Nothing was changed." (path shown with `to_stored()`), and an invalid flavor name with "The unfinished change names a game version folder that is not valid. Nothing was changed." This is the M1 refusal-wording checkpoint, taken per R4.
- T1.2: no new event for the refusal: it is an `UndoError` the review's `start_run` already handles as an expected refusal, like the locked-file and WoW-running refusals.
- T1.2: departure from the sketch: `_moved_zip` now takes the name with `PureWindowsPath(zip_path).name`, because on a non-WSL POSIX host `to_native()` leaves a Windows-form path as one path component and `.name` would be the whole string.
- T1.2: CHANGELOG gains an `## [Unreleased]` section with a `### Fixed` group (the first post-0.1.0 entry), following the 0.1.0 entry's tool-grouped bullet style.
- T1.3: the finished-journal check runs first in `recover`, before the flavor and WoW-running checks: it changes no file (it only removes the marker), so neither guard is needed; the review screens still run their own WoW preflight before calling `recover`.
- T1.3: R2's rule is widened for files without an `edited` entry (review fix): a file the run skipped in its write loop (CHANGED) or rolled back has no entry, so recovering it the old way would put back every other file of a run that finished (the F-002 failure). Such a file now counts as consistent with a finished run when it is in the WTF folder and its current hash is not the marker's `after` (the run never left it written; normal recovery would not touch it either). A file that is at `after` with no entry still sends the run down the normal path, since the journal cannot tell it was written. At least one `edited` entry is still required. (Superseded in part by the `completed` record bullet below: the edge noted here, a stopped run with a failed put-back, was wider than first thought.)
- T1.3: zip names are compared with `PureWindowsPath(...).name` on both sides, like `_moved_zip` (T1.2), so a marker or journal written on the other OS still matches.
- T1.3: departure from the sketch: the test plan's `recover` result is `UndoResult(stale_marker=True)` (a new field) rather than a bare empty result, so the screens can tell "finished, marker removed" from "nothing to put back"; the post-recovery notice moved to the shared `sv_report.recovered_notice` (both review screens had the same text, STD-2.2).
- T1.3: no retry or event for the `_roll_back` path's `clear_marker`: a marker left there names files already at their original, which recovery records and clears without changing anything.
- T1.3: review fix: recovery and Leave as is check `clear_marker`'s result too. A marker still there is `UndoResult.marker_left`; `marker_stale` (stale path) or `recovery_done` (put back, leave) is logged at warning with a `marker_left` field rather than a new event, so the existing events stay the one record of each outcome; `recovered_notice` / `leave_notice` say the marker is still there and the next scan offers it again (warning), and both review screens keep `self.marker` so Apply offers it again. The put-back path's unchecked removal was harmless (files already at their originals) but is reported the same way for consistency.
- T1.3: review fix: Leave as is moved into core as `sv_undo.leave(tool, marker, root=)` (the SV Browser had it in its `undo.py`, the Ace3 Profile Manager inline in its review screen; STD-2.2); each tool's `undo.leave` wraps it. `ace.recovery_done` for leave now also carries `flavor` and `zip`, like `svb.recovery_done`.
- T1.3: review fix (blocker): the run-level `finished` line is written by `apply_flavors` whenever the journal has entries, also after a flavor stopped (ApplyError, or Ctrl+C) with a failed roll-back, the very case the marker is kept for; a stopped run then looked finished and recovery dropped it (a file left edited, or a half-written file not in the journal). Chosen fix: a per-flavor `completed` journal line (flavor + zip), written by `_apply` only after its write loop ran without an exception and only when it edited a file, before the marker is removed; `_finished_journal` requires it instead of `finished`. Over skipping `finish()` on a stop because it is per flavor: in a multi-flavor run, flavor 1 completing and flavor 2 stopping still marks flavor 1 (whose marker it would be) correctly. It is written with `_write`, not counted as an entry, and `read_edit_journal` drops it, so Undo, `latest_undoable` and `referenced_zips` are unchanged. If writing it fails, the flavor is treated as unfinished (recovery puts back what is still at `after`: the safe side). Journals written before this change have no `completed` line, so their stale markers recover the old way (no released version wrote them).
- T1.3: in a multi-flavor Apply, a marker left after one flavor makes the next flavor's earlier-marker refusal stop the run (as before); the result shows both the "Crash marker" row and the stop, and recovery then clears the stale marker. Not changed, to keep the refusal the one guard against overwriting a marker.
- T2.1: the review's sketch was followed as written; the late recheck sits after the dry-run return, so a dry run is unchanged. A file that vanished between the snapshot and the delete is now `skipped` / `missing` rather than `failed` (the unlink's `FileNotFoundError`), matching the early recheck. No new event: `sv.skipped` already covers it.
- T2.2: departure from the sketch: a rollback failure is caught as `BaseException` (not `OSError`), so a second Ctrl+C during the rollback still ends in the message that names the backup folder rather than a traceback.
- T2.2: on Ctrl+C the CLI prints a fixed notice (`UPDATE_STOPPED`) instead of a traceback: the install was put back for a zip install; the notice tells a git checkout to check `git status`, since an interrupted `git merge --ff-only` is left to git and the review did not cover the git path. `_auto_update` re-raises after printing, so Ctrl+C at start still exits (130) rather than opening the menu. No new event: `update.failed` covers the interruption.
- T2.2: review fix: a Ctrl+C after the new version is in place is swallowed, not re-raised: the update is applied, so the CLI prints the normal "Updated ... Restart" message and exits 0, and an automatic update exits 0 as after any update. A new warning event (`update.cleanup_stopped`) records it rather than reusing `update.failed`. A failed rollback during an automatic update exits with code 1 (the message names the backup) instead of re-raising, since the user needs that message, not a traceback.
- T2.3: the review names the Undo function `undo.undo`; the actual function is `undo.undo_restore`, which is what the call-site test pins.
- T2.3: no `CHANGELOG.md` line: the swap already refused leftover `.restoring` / `.replaced` folders, and on POSIX `os.rename` only replaced an *empty* folder that appeared in the gap, so no normal run behaves differently (STD-11.1).
- T2.3: no new behavioural test for folders: `rename_no_replace` hard-links first, which a directory refuses (`EPERM`), so a folder rename takes its documented best-effort fallback (last `lexists` check, then `os.rename`); the guarantee is pinned by the signature test the test plan names, and `rename_no_replace` itself is covered in `test_fsutil.py`. Links moved by `_move_links` are hard-linked as links (`follow_symlinks=False`) and get the atomic refusal, except on WSL's drvfs (see the review fix below).
- T2.3: review fix: `EISDIR` from `os.link` is treated as "no hard link" for every caller of `rename_no_replace`, not only Interface Backup: an existing target gives `EEXIST`, never `EISDIR`, so the refusal is unchanged. No CHANGELOG line: the drvfs failure only existed on this unreleased branch.
- T2.3: one full-suite run had a single failure that did not recur in three further runs (all 1744, 0 failures); its output was not kept, so the test is not known; `-k interface_backup` (239 tests) and the call-site tests were green each time, so it was taken as an unrelated timing flake.
