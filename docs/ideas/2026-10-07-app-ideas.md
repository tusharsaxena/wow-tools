# App ideas: out-of-game tools (2026-10-07)

Brainstormed on 2026-10-07 by a multi-agent ideas workflow: nine idea generators (one per angle: WTF and SavedVariables, the AddOns folder, logs, media, multiple installs, addon development, public web APIs, player pain points found on reddit and forums, wildcards), a merge and dedupe pass, three independent judges, and a completeness critic that added the `X` ideas.

**Constraint:** every idea runs on data available outside the game: files on disk, the user's own addon repos, or public web APIs. No in-game API, injection or memory reading, and nothing against Blizzard's terms. The critic found no idea that breaks it. Caveats: anything that downloads from CurseForge honours authors' third-party distribution opt-out and needs the user's own API key; Raider.IO and Warcraft Logs lookups follow those sites' API terms (no bulk scraping); Blizzard's build-version endpoints are public but undocumented.

**Scores** are 1 to 10, averaged across three judges (a heavy retail player, the suite's maintainer and addon author, and a Python engineer who knows `wowtools/core/` and `wowtools/ui/`). *Usefulness* 10 means used weekly or a big chore removed. *Difficulty* 1 means a weekend on top of the existing shared code, and 10 means months, fragile formats or heavy infrastructure. ★ marks an idea from the existing backlog.

These are ideas, not decisions: none is planned or approved.

## The ideas in detail

### I03 Addon Update Checker

Usefulness 8.3/10 · Difficulty 6.7/10 · from the backlog

Finds each installed addon's real source from the project IDs packagers already write into TOCs, compares the installed version with the newest release, flags TOCs behind the live client build, and can optionally update with a backup first and Undo.

**How it works:** Source resolution, in order:
1. TOC fields X-Curse-Project-ID, X-Wago-ID, X-WoWI-ID, and X-Github or X-Website pointing at github.com.
2. A .git folder inside the addon, reported as a dev checkout and never updated.
3. A fuzzy Title/folder match against WoWInterface's public file list (api.mmoui.com), which the user confirms once; the choice is saved in config.
Multi-folder addons (DBM-*, ElvUI_Options) are grouped by shared source ID. Versions are compared by release date and file ID before the version string, since many are not semver. Live builds come from Blizzard's public TACT version endpoint (us.version.battle.net/v2/products/<wow|wowt|wow_classic|wow_classic_era|wow_beta>/versions), mapped to an interface number, so 'Interface behind live' shows without asking the user. Sources: GitHub Releases (the core/updater client, optional PAT), WoWInterface (public), CurseForge Core API and Wago API only with the user's own key. Results are cached with a throttle like the updater's 24 h cache. The tree groups addons into Update available / Up to date / Unknown source / Dev checkout / Interface behind live; the detail pane shows remote version, date, changelog excerpt and flavor compatibility. Optional update mode, off by default:
- download into staging;
- verify the zip layout (top-level folders each contain a TOC, no paths escape staging, size limits);
- zip the current folders as a backup;
- swap folder by folder with rename_no_replace;
- journal and crash marker, Undo for the last update.
Updates are refused while WoW runs. Ship the report-only mode first.

**Data sources:** Interface/AddOns/*/*.toc and .git folders; Blizzard TACT version endpoint; WoWInterface API; GitHub Releases API; CurseForge Core API and Wago Addons API (user-supplied keys)

**Why it is useful:** Usefulness 9/10. Difficulty 7/10 (8/10 with installs). This is the main reason players keep the CurseForge/Overwolf app installed. Reading project IDs from TOCs makes source detection exact for most addons. It is also the only checker that recognises the user's own dev checkouts and links, and it answers the patch-day question 'what will break' before login.

**Reuses:** core/updater (GitHub release fetch, injectable opener, throttle cache, SHA-256), core/install, core/process, core/backup, core/fsutil.rename_no_replace, core/journal + marker + undo, core/config + ui/settings_form (keys, sources), ui/review, ui/result_screen. A new shared core/webapi.py (cache, ETag, backoff, injectable opener) and core/addon_sources.py, reused by I04, I14, I45 and I46.

**Risks:** CurseForge and Wago need keys and have terms of use: never ship a key, the user brings their own, and it is never logged. Fuzzy matches go wrong, so mappings are always confirmed. Install mode is effectively a small addon manager and must stay staging-first behind the full safety net. Endpoints change, so keep one adapter per source and mock the network in tests (STD-10).

**Judges' notes:** Report-only is about a 5 and should ship first. Installing is an 8, because CurseForge downloads need a key and many projects block third-party distribution. · The report-only mode is about difficulty 4 and should ship first. Updating needs CurseForge and Wago keys plus the staging installer, which is where the difficulty jumps. · Report-only via TOC IDs, GitHub and WoWI is about difficulty 5. CurseForge and Wago need keys and have ToS limits on third-party clients, and the installer adds the most data-safety work.

### I20 Lua Error Inbox

Usefulness 7.3/10 · Difficulty 3.3/10

Turns the errors BugGrabber/BugSack saved to disk into a de-duplicated, per-addon issue inbox, maps stack frames to file:line in your own repos, and drafts redacted GitHub issues for Ka0s addons.

**How it works:** Parses BugGrabberDB.errors (message, stack, locals, counter, session, time) from every account's !BugGrabber.lua with luasv (parse_at for big files). Each message is normalised into a signature (line numbers, addresses, table:0x ids and player names stripped, top 3 frames kept). Errors are grouped by signature and attributed to the first Interface/AddOns/<X>/ frame, then joined with that addon's TOC Version, project IDs and the client build from .build.info. The first error of each session is highlighted, since the later ones are usually consequences. The user's own addons are pinned at the top (configured names or repo roots). For those, each frame maps to the local checkout's source line, with a warning when HEAD differs from the installed version. Groups are ranked by count x recency, with first and last seen and sessions affected. 'Draft issue' builds a Markdown body (signature, stack, locals, versions, flavor, build) after a redaction pass and preview, then copies it to the clipboard or file, or runs `gh issue create` only after an explicit confirm. Third-party addons get project-page links. 'Mark seen' is kept in suite state. Optional 'trim old errors' goes through the SV pipeline with snapshot and Undo.

**Data sources:** WTF/Account/*/SavedVariables/!BugGrabber.lua and BugSack.lua, Interface/AddOns/*/*.toc, .build.info, the user's local addon repos, GitHub through the gh CLI (opt-in)

**Why it is useful:** Usefulness 8/10 (10/10 for this addon author). Difficulty 4/10. BugSack shows one error at a time in game, with no grouping across sessions and no link to source. This turns weeks of collected evidence into a triaged, source-linked bug list, and tells normal players which addon to blame or update.

**Reuses:** core/luasv, core/svfiles, core/install, core/sv_apply/sv_journal/sv_undo (trim), core/events, ui/review, ui/tree_filter, ui/warnings_view, ui/settings_form (repo roots)

**Risks:** It needs BugGrabber installed; otherwise show a clean 'not found' state. The schema changes between BugGrabber versions. Locals can hold names or chat, so redact and preview. Network or GitHub actions are explicit, confirmed every time, and mocked in tests.

**Judges' notes:** Low for players, 8 for an addon author. The parser is straightforward on top of luasv. · Very high value for an addon author with little new code (luasv already parses the data), and the cheapest of the strong ideas. · BugGrabber's format is stable and luasv already parses it. Strong fit for an addon author.

### X09 Session Watcher: auto-backup on game exit and playtime coach

Usefulness 7.3/10 · Difficulty 3.7/10

While the suite is open, it notices when WoW starts and exits. After every session it runs a quick incremental WTF / SavedVariables backup (so a later corruption costs one session, not a week), and it keeps an honest local diary of play time with optional weekly budgets and break reminders.

**How it works:** Data: the process list (the existing running-game check, polled every few seconds), file modification times under WTF and SavedVariables (to confirm the client finished writing), and the Logs folder timestamps. Algorithm: a small state machine (idle -> game running -> game exited -> files stable for N seconds -> backup); the backup is a content-hash incremental zip (only changed SV files) with rotation (keep last 20 sessions plus a daily and weekly ladder); session start and end times go to a local journal for the time stats. UI: a status pane (watching, last session, last backup, health check of the latest zip), a week heatmap of play time, and settings for budgets and reminders (a desktop notification after X hours). Writes: only backup zips in the backup folder and its own session journal; never touches the WoW folder.

**Data sources:** Process list, WTF/ and SavedVariables mtimes and contents, Logs/ timestamps

**Why it is useful:** Interface Backup is manual, and people forget to run it. The SV losses that I06 tries to rescue after the fact are mostly prevented by an automatic per-session snapshot. The play-time half serves the wellbeing persona (a parent or a player who wants limits) that none of the 48 ideas covers; I48 is only a yearly look back. Usefulness 8/10 for the backup half, 5/10 for the coach half. Build difficulty 4/10.

**Reuses:** core/process.py (running-game detection), core/backup.py (verified zip creation), core/snapshot.py, core/fsutil.py, core/lock.py, core/install.py (flavors and paths), core/journal.py, ui/settings_form.py, Interface Backup's restore flow for getting a session back

**Risks:** The suite rule that tools never start on their own and have no background mode (CLAUDE.md, the standards) means it only watches while its screen is open. A true background service would need a documented deviation in standards.md, so flag it to the user rather than building it silently. File-stability detection must not back up half-written SVs (wait for the mtimes to settle after the process exits).

**Judges' notes:** The best of the batch. An automatic incremental SV backup after every session takes away the 'my WTF got wiped' disaster with no effort from the player. Nearly everything already exists in core: the running-game check, zip backups and rotation. The playtime coach is an optional extra. One catch: it only works while the suite is open. · Builds directly on Interface Backup and the running-game check, and covers the most common real loss (corrupted SVs). The catch is that it only works while the suite is open, so a tray, service or scheduled mode would make it much stronger. The playtime diary is a nice extra. · Best value for the effort. It reuses the running-game check, the zip backups from Interface Backup and the journal. The main limit is that it only works while the suite is open, since the suite has no daemon or tray mode. New work: the debounce state machine, incremental content-hash zips with rotation, and cross-platform desktop notifications.

### I05 WoW Doctor

Usefulness 7.0/10 · Difficulty 4.3/10

A one-key health check of the whole install. It finds the common 'my addon doesn't show up / my settings don't save' causes and sends each finding to the tool or manual step that fixes it.

**How it works:** Independent read-only probes, each returning Finding(severity, evidence path, explanation, remedy):
(1) Mis-nested unzips (AddOns/Foo/Foo/Foo.toc), GitHub '-master'/'-main' folder suffixes, a folder with no TOC, a TOC name that differs from its folder, stray .zip/.rar/__MACOSX.
(2) TOC Interface behind the client build from .build.info (header-name parsing of the pipe table, multi-value Interface lists, _Mainline/_Classic/_Vanilla/_Cata/_Mists suffix precedence).
(3) A missing or disabled RequiredDep; LoadOnDemand addons with no LoadWith or LoadManager installed; orphan module folders (DBM-* without DBM-Core); dependency cycles; reverse-dependency impact ('removing BigWigs_Core disables 14 addons').
(4) Unreplaced @project-version@ tokens.
(5) Two folders differing only by case, or the same addon twice under different names.
(6) WTF under OneDrive/Dropbox, or read-only attributes on WTF files.
(7) Config.wtf oddities (scriptErrors 0, a forced legacy gxApi).
